# Evolve 自主进化复研

## Overview

以档案库根为持久状态，让调研"越用越准"：复用旧证据、只查增量、修订结论、记录演变、按需自动重访。

## 档案库约定（单源，deep-research 同样遵循）

### 档案库根解析（写入前必做）

档案库根（archive root）是所有档案的实际落盘位置，默认当前工作区下的 `research/`。**写入任何档案前必须先解析根目录**，不得直接假定 `research/` 可写：

1. 默认根 = 当前工作区的 `research/`。
2. **占用检查**：解析时先看 `research/` 是否已存在且**不是本插件的档案库**（本插件档案库的特征是含 `research-log.jsonl` 标记文件）。
   - 不存在 → 直接使用 `research/`。
   - 存在且含 `research-log.jsonl` → 是本插件自己的档案库，正常使用。
   - 存在但**不含** `research-log.jsonl` → 是用户项目里原有的同名目录（可能是学术 `research/`、文档目录等），**不得写入**——覆盖或混入他人内容不可逆。
3. **回退路径**：上条命中时，改用当前工作区下的 `research-evolve/`（同样先做占用检查：已存在且不含 `research-log.jsonl` 时同样不得写入）。
4. 两条路径都不可用时**停止**，向用户说明冲突并请其指定档案库根，不得强行写入任一目录。

解析结果在本次任务内保持一致（同一批操作写同一个根）；判定依据要向用户明示用了哪个根。

> 本节是档案库根解析的**唯一定义处**。deep-research、benchmark、visual-report 三个技能只引用本节，不各自复述判定规则——规则复制即漂移。

### 目录结构

```
<档案库根>/
  INDEX.md               # | slug | 标题 | 最后复研 | 当前置信度 | 建议下次复研 |
  research-log.jsonl     # 每行一事件，append-only
  <slug>/
    notes.md             # 累积事实片段（复研的差量基线）
    report-YYYYMMDD.md   # 各期报告，永不删除旧期
    report-YYYYMMDD.html # 可视化产物（由 visual-report 生成）
```

`research-log.jsonl` 行 schema：

```json
{"date":"2026-10-16","topic":"<slug>","action":"research|revisit|report|score|schedule","summary":"一句话变化","confidence":"high|medium|low"}
```

## 三种指令

### `revisit <slug>`（核心回路）

1. 先按「档案库根解析」定根，再读 `<档案库根>/<slug>/notes.md` 与最新一期报告，提取"当前结论 + 置信度 + 报告日期"作为基线。
2. 只检索增量：查询词强制带时间限定（如 "after:2026-09"、版本号、"2026 最新"），目标回答两个问题——旧结论是否仍成立？有无推翻性新证据？
3. 差异判定，三选一：
   - **维持**：无实质变化 → 不改报告，只更新 INDEX 的"最后复研"日期与 log。
   - **修订**：局部变化 → 在最新报告末尾追加 `## 修订 YYYY-MM-DD` 段（原结论/新证据/修订后结论/置信度变化），旧结论保留不删，形成可追溯演变链。
   - **推翻**：出现相反的一手证据 → 新写一期 `report-YYYYMMDD.md`，摘要里显式声明"推翻上期结论 X，原因……"，并 log。
4. 每次 revisit 结束输出简短对比：`上期结论 → 本期结论（置信度 高→中，因单新源冲突）`。

深度控制：revisit 检索预算默认为首次调研的 1/3；若发现推翻性信号再升级为完整 deep-research。

### `list`

读 INDEX.md 输出主题台账总览（主题、置信度、距上次复研天数、建议动作），并按 staleness 排序提示哪些主题该 revisit。INDEX 缺失时从档案库根目录扫描重建。

### `schedule <slug> <周期>`（自动进化入口）

若宿主提供定时任务工具（cron 类 MCP 工具或宿主内置调度）：

1. **确定调用形态**：不同宿主暴露技能的方式不一致（`/<插件名>:<技能名>`、仅 `/<技能名>`、或根本不支持斜杠命令而只认自然语言描述），**不得凭猜测拼命令**。做法是观察当前会话里技能的实际调用形态——宿主自身的技能清单、已注册的命令列表、用户此前的调用示例都是依据；看不出来时按自然语言描述写。
2. **写 payload**：优先用**自然语言**描述任务，不依赖斜杠命令语法——「自动定时复研，沿用既有档案基线；无变化则只更新 INDEX」，并带上 `revisit <slug>` 的语义（主题 slug + 动作）。这样跨宿主都不需要改写命令前缀。若确认宿主走斜杠命令形态，再按第 1 步观察到的实际形态补前缀。
3. **回读校验**：创建后**回读**该定时任务，确认周期与 payload 与预期一致（周期错误、slug 丢失、命令拼错都会让任务静默空跑）。不一致就改写任务，而不是留着等它跑歪。
4. 周期建议：快速变化领域（前端框架/AI 模型）7–14 天；缓慢领域（数据库、标准）30–90 天。
5. 创建前向用户确认周期与通知方式；把 cron 任务 id 写入该主题 notes.md 头部注释，log 记 `action:"schedule"`。
6. 宿主无定时工具时，退化为在 INDEX“建议下次复研”列写入目标日期，由人工或下次会话触发。

## 硬约束

- 只读增量检索同样遵守 deep-research 的引用与置信度规则，禁止无证据改判。
- 旧报告与旧 log 行是不可变历史：只追加，不改写、不删除。
- 写入仅限档案库根（按上文「档案库根解析」判定的目录），不动业务代码与用户项目里的其他目录。
- 连续两次 revisit 均"维持"且主题非跟踪型（log 无 schedule）时，提示用户可延长周期或退役该主题（移入 INDEX"已归档"节），避免无效检索烧钱。
