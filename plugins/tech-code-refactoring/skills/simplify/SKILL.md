# Simplify 行为不变的减法

## 何时用

- 重构收尾阶段做最后一轮减法，或用户要求「清理这段代码」时。
- 前提：目标行为已被测试覆盖，或可用特征对照等价验证。
- 不适用：需要改结构的手法（提取/搬移/多态化交给 code-refactoring）；架构边界调整（交给 system-architect）。

## 总纲

只做减法，不做加法；每一步删除或收缩，都必须能证明「对外行为不变」。证明不了的不删。

推荐操作顺序：先删死代码（缩小面）→ 再去防御性默认 → 合并重复分支 → 缩嵌套 → 最后收窄公共 API。前面的步骤会让后面步骤的引用检索更准、证明更容易。

## 行为不变的证明手段

| 手段 | 适用 | 合格标准 |
|---|---|---|
| 全量测试 | 有测试覆盖的目标 | 测试集合不变且全绿 |
| 构建/加载 | 一切删除与可见性收缩 | 构建通过，无遗漏引用报错 |
| 引用检索 | 死代码、导出符号 | 全仓检索引用为零，检索范围含字符串与反射式调用 |
| 特征对照 | 合并分支、缩嵌套 | 相同输入在改造前后得到相同输出 |

一次操作至少用两种手段证明；两种都给不出的，不删。

## 五类操作与验证方式

### 1. 删死代码
- 对象：不可达分支、永不命中的条件、无引用的私有函数与变量、被注释掉的旧代码块。
- 前置证明：全仓引用检索为零；并以 code-analyzer 报告或 agent-git-oracle 孤儿清单佐证。
- 验证：删除后全量测试绿 + 构建通过；无测试覆盖时至少编译/加载通过，并逐项列出删除内容请用户复核。
- 红线：公共 API 与导出符号不在本类操作范围（见第 5 类）。

### 2. 去防御性默认
- 对象：对内部调用方重复校验不可能出现的空值、给内部函数兜底的静默默认值。
- 前置证明：逐个调用点确认输入由内部保证，不存在外部输入路径。
- 验证：测试绿；若删除兜底后测试暴露真实外部路径，立即恢复并改判「不能删」。
- 红线：一切接受外部输入的边界（网络、文件、用户输入、跨进程）校验一律保留，不适用本类。

### 3. 合并重复分支
- 对象：if/else 两支或 switch 多支尾部执行完全相同的代码。
- 前置证明：逐行比对各分支，差异为零才算重复。
- 验证：测试绿；对该分支的每个取值做改造前后特征对照（相同输入必须得到相同输出）。

### 4. 缩嵌套（早返回）
- 对象：三层以上的 if/for 嵌套，主逻辑被埋在深层。
- 做法：把异常与前置检查逐条提为开头卫语句并早返回，主路径保持一层缩进。
- 验证：每提一条卫语句跑一次测试；对照改造前后的路径集合（正常路径 + 每条卫语句路径）行为一致。

### 5. 收窄公共 API
- 对象：模块导出了从未被外部使用的符号。
- 前置证明：跨全仓引用检索为零，且不属于框架或插件约定必须导出的面。
- 做法：去掉导出、改为模块私有；只收缩可见性，不改名字与签名。
- 验证：构建通过（导出面变化会在编译/加载期暴露遗漏引用）+ 测试绿。
- 红线：重命名、改签名、搬移位置属于对外可见变更，交 code-refactoring 并先经用户确认；本类只做「从可见变不可见」。

## 明确不做的事

- 不顺手改格式：空格、引号、换行、import 排序一律不动，避免污染 diff 与审查。
- 不改注释措辞：注释语句再别扭也不动，除非整段随代码一起删除。
- 不重命名公共 API、不迁移调用方：对外可见变更归 code-refactoring 的搬移类手法，且需先确认。
- 不夹带顺手优化：发现性能问题、疑似 bug 只记录上报，不在减法里顺带处理。
- 不删本次范围之外的既有代码：哪怕它看起来明显是死的，也只列为候选，报给用户决定。

## 产物

- 原子提交（按类或按文件分组），diff 只含删除与可见性收缩。
- 一份减法清单：每条 = 删了什么 + 依据（引用检索结果）+ 验证方式与结果；「存疑未删」的候选单独列出，附文件路径与疑点，供下一轮侦债或用户复核。

## 何时停

- 任何一步给不出行为不变的证明：跳过该项并记录原因，不强删。
- 删除后测试或构建变红且回滚后无法定位原因：回滚本类全部操作，上报阻塞。
- 需要超出减法范围的动作（改签名、跨模块搬移、新依赖）才能继续：停止并向用户确认。
- 检测到目标文件存在未提交的外部改动：停止，避免与并行修改互相踩踏。
