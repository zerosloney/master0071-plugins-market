# Refactoring Workflow 六步编排路由

## 定位

技术债重构的入口与总调度。接到重构类请求时，先判断走哪条路，再逐步调起对应技能；自己不直接评审、不直接改代码，只做路由、产物验收与出圈保护。

## 六步编排

```
① code-analyzer 量化摸底
        │  report.md（复杂度/依赖/循环依赖 + 人工研判）
        ▼
② agent-git-oracle 历史侦债
        │  热点与债区清单 + 重构优先级建议
        ▼
③ uncle-bob 质量评审
        │  按文件分级的 P0-P2 findings
        ▼
④ code-refactoring 执行重构
        │  原子提交 + 重构记录
        ▼
⑤ system-architect 架构对齐（仅当债区反映结构问题）
        │  ARCHITECTURE.md + ADR
        ▼
⑥ simplify 减法收尾
           减法清单 + 干净工作树
```

各步验收：每步结束核对产物存在且关键数字齐备，才进入下一步；产物缺失时重跑该步，不带着空洞推进。

调起方式：按技能名逐步调起对应 SKILL.md，并把上一步产物路径作为输入传给它；宿主支持插件命名空间时写作 `/<插件名>:<技能名>`，否则直接用技能名。

批量策略：债区多于三个时，只取优先级清单前三名进入本轮③④步，其余排队等下一轮——一轮流程只吃一批，防止改动面失控。

## 路由规则

| 步骤 | 何时进入 | 何时跳过 |
|---|---|---|
| ① code-analyzer | 首次接触该代码库；或现有报告超过一个月未更新 | 用户已提供新鲜量化报告；纯单文件小修 |
| ② agent-git-oracle | 摸底显示热点集中，需要定优先级 | 仓库无 git 历史；用户只关心指定文件本身 |
| ③ uncle-bob | 任何修改开始前评审一次 | 用户已给出明确评审结论 |
| ④ code-refactoring | 评审存在 P0/P1 且用户确认要修 | 只有 P2 或纯删除任务 |
| ⑤ system-architect | 债区、循环依赖或强共变组指向模块边界问题 | 问题全部在文件内部；用户未要求架构产出 |
| ⑥ simplify | 每次修改完成后默认收尾 | 用户明确不要收尾清理 |

轻道：单文件小任务跳过①②⑤，直接走 ③→④→⑥；轻道的③只评审目标文件。

步骤⑤进跳细则：

- 循环依赖 ≥ 1 条，或强共变组跨目录 → 进入。
- 债区全部落在单文件内部 → 跳过，但把该结论写进最终汇报。
- 拿不准 → 交用户决定，不默认进入。

## 出圈保护（任一命中立即停下）

1. **行为改变**：任何一步发现不得不改变对外行为才能继续——停下，向用户说明差异，等待决策。
2. **跨模块扩散**：④或⑥的改动开始蔓延到目标目录之外——停在工作区边界，回报牵连面。
3. **需要新依赖**：任何步骤想引入第三方库或新构建步骤——停止，重构流程不允许自带依赖。
4. **公共 API 变更**：重命名、改签名、迁移调用方——先列出影响面请用户确认，再继续。
5. **中断恢复**：流程被打断时，按下方产物清单核对已完成步骤，从最后一份完整产物续跑，不推倒重来。

## 六步产物清单

| 步骤 | 产物 | 验收标准 |
|---|---|---|
| ① | report.md | 三章节齐备，含人工研判小节 |
| ② | 热点与债区清单 | P0/P2 分级有 churn 与复杂度数字支撑 |
| ③ | 评审报告 | 按文件分组、P0-P2 分级、头部有汇总 |
| ④ | 原子提交 + 重构记录 | 每手法一提交、测试全绿、行为不变 |
| ⑤ | ARCHITECTURE.md + ADR | 五章节齐备、决策有编号与量化依据 |
| ⑥ | 减法清单 + 干净工作树 | 每条删除有行为不变证明 |

## 何时停

- 用户目标只是问答或咨询：不进入流程，直接回答。
- 第一步摸底就失败（缺 Node 环境、路径无效、脚本报错）：回报阻塞，不跳过摸底硬闯后续步骤。
- 全程纪律：每步产物经手核对后才推进；出圈信号未决时保持工作树干净，原地等待指令。
