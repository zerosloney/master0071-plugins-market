# System Architect 目标架构与模块化

## 何时用

- agent-git-oracle 的债区、强共变组或 code-analyzer 的循环依赖显示问题出在模块边界而非单文件质量时。
- 用户要求「梳理模块划分」「画一下架构」「写架构决策记录」。
- 不适用：单文件内部质量问题；没有量化底数就想定架构——先跑 code-analyzer，不拍脑袋。

## 差距分析法（现状 → 目标）

1. **取现状底数**：读 code-analyzer 的 `report.md`，摘出依赖热点、循环依赖、分层越界提示；缺报告则先跑摸底，不跳过。
2. **取演进证据**：读 agent-git-oracle 的债区清单与共变组，标出「逻辑上是一个模块、物理上被拆散」的文件组。
3. **画现状图**：以现有目录结构与依赖计数为准画模块图，禁止凭想象补画不存在的层次。
4. **定目标状态**：对每个问题给出目标态（谁该依赖谁、边界在哪），并写明判断依据（共变组、依赖计数、业务语义），禁止无依据地空谈最佳实践。
5. **列差距清单**：现状到目标逐条列出，每条标注影响面与迁移代价（小/中/大），作为演进路线的原料。

## 模块化准则（可操作判据）

设计或评审模块边界时逐条核对，四条全过才算边界成立：

| 判据 | 合格标准 | 核对方法 |
|---|---|---|
| 依赖方向 | 只允许上层指向下层、或指向抽象；禁止下层反向依赖上层 | 对照依赖热点与分层提示，逐条检查反向引用 |
| 无环 | 任何模块级环路都视为边界缺陷 | 以循环依赖清单为准，每个环必须给出消除方案 |
| 公共面大小 | 模块对外暴露的入口越少越好；仅内部使用的符号不导出 | 数模块被外部引用的符号数，与内部符号总数对比 |
| 共变内聚 | 同模块的文件应倾向一起变化 | 对照共变聚类结果，跨模块强共变即边界画错的证据 |

有违反的条目全部进入差距清单，不因「历史原因」豁免。

## ADR 决策记录

每个架构级决定单独一份 `ADR-NNN-<标题>.md`（编号递增，放仓库约定的 docs/adr/ 或同等目录），固定结构：

```markdown
# ADR-NNN：<决策标题>
- 状态：proposed | accepted | superseded by ADR-MMM
- 日期：YYYY-MM-DD

## 背景
问题与约束，引用量化证据（报告章节、共变组、依赖计数）。

## 决策
一段话说清选了什么。

## 理由
为什么选它，为什么放弃其他候选（候选至少列一个）。

## 影响
需要迁移的模块、代价分级、对应演进路线条目。
```

规则：一次决策一份 ADR，不合并；推翻旧决策时新增 ADR 并把旧的标为 superseded，不删不改旧文件。

## 产出 ARCHITECTURE.md 骨架

在用户指定位置（缺省仓库根）生成或更新 `ARCHITECTURE.md`，固定五章节：

```markdown
# ARCHITECTURE

## 1. 上下文
系统是什么、服务谁、与哪些外部系统交互。

## 2. 模块图
文本图（缩进树或 mermaid）；节点与真实目录一一对应，禁止画理想化的不存在模块。

## 3. 依赖规则
允许的依赖方向与禁止项逐条列出，每条注明来源 ADR 编号。

## 4. 边界清单
每个模块一行：入口符号、对外承诺、禁止外部触碰的内部实现。

## 5. 演进路线
差距清单按代价从小到大排序：每条 = 现状 → 目标 → 代价 → 负责技能（code-refactoring 或 simplify）。
```

## 产物

- `ARCHITECTURE.md`：五章节齐备，模块图与真实目录可逐一对照。
- ADR 文件：每份决策有编号、状态与量化依据。
- 差距清单：已折叠进演进路线章节，条目可直接派给执行技能。

## 何时停

- 缺量化底数（摸底报告与 git 证据都缺失）且用户不同意先跑摸底：停止，不做无证据的架构设计。
- 目标架构需要推翻既有公共 API 或跨仓库改动：停止，把方案与影响面交给用户决策。
- 只写文档不动代码：执行类改动留给对应技能，本技能的交付物是决策与路线。
