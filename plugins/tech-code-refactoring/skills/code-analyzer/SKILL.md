# Code Analyzer 深度结构分析

## 何时用

- 重构、架构评审或接手陌生代码库之前，需要一份客观的量化底数。
- 用户问「哪里最复杂」「哪些文件被依赖得最多」「有没有循环依赖」。
- 作为 refactoring-workflow 六步编排的第一步，为后续技能提供热点清单。
- 不适用：只改一个函数的小任务；纯语义问题（脚本只看结构，不懂业务含义）。

## 调用方式

在仓库根目录执行（固定接口，`<>` 为必填、`[]` 为可选）：

```
node <skill目录>/scripts/analyze.mjs --path <目标> [--output report.md] [--exclude 片段] [--heuristic]
```

- `--path`：目标文件或目录；建议先从目录级摸底，再对热点下钻到文件级。
- `--output`：缺省时打印到标准输出；正式摸底务必落盘为 `report.md`，供后续技能引用。
- `--exclude`：不参与统计的路径片段，可重复传入；典型排除项为构建产物、第三方 vendored 代码、生成代码目录。
- `--heuristic`：强制全库走启发式层（跳过 AST 引擎）；正常分析无需此参数，用于测试与对比。
- 环境要求：Node ≥ 18（含 WebAssembly 支持），零外部依赖；AST 引擎为随插件分发的 vendored tree-sitter，无需安装任何包。

典型调用序列（目录摸底 → 热点下钻）：

1. 目录级：`node <skill目录>/scripts/analyze.mjs --path src/ --output report.md --exclude node_modules --exclude dist`
2. 读报告，定位复杂度排名前 3 的文件。
3. 文件级下钻：`node <skill目录>/scripts/analyze.mjs --path src/<热点文件> --output hotspot-report.md`
4. 在每份报告末尾各补一节人工研判。

## 报告章节怎么读

拿到 `report.md` 后按问题对号入座，不要通读全部数字：

| 章节 | 回答的问题 | 读法 |
|---|---|---|
| 复杂度热点 | 「改哪里收益最大？」 | 「函数级复杂度热点 top10」是重构优先级的第一信号：函数级圈复杂度排名靠前且近期仍被修改的函数优先处理；再看文件级圈复杂度与函数长度排名定位热点文件 |
| 依赖热点 | 「动哪里牵连最广？」 | 被引用次数最高的文件；它们是公共面，改动要保守，动手前先看调用方 |
| 循环依赖 | 「哪些模块纠缠在一起？」 | 环上的文件清单；环是模块边界失控的直接证据，移交 system-architect 处理 |

三条铁律：

1. 热点只是候选，不是判决——数字高的文件可能只是生成代码或测试夹具，先人工确认再定优先级。
2. 复杂度热点要与变更频率（agent-git-oracle 的产出）交叉，两个维度都高的才是真债区。
3. 循环依赖单独列出，不与单文件复杂度混排比较。

## 分析引擎与分层降级

报告概览的「分析引擎」一行如实披露每个文件实际走的引擎：`AST ×N 文件 / 启发式 ×M / 仅计数 ×K`。

- AST 层（默认）：随插件分发的 vendored tree-sitter，覆盖 9 种语言（JS/TS/TSX、Python、Java、Go、Rust、C/C++）；函数级与文件级精确指标、函数级复杂度热点、依赖图精确提取均出自这一层。
- 启发式层（降级路径）：vendor 资产缺失、WebAssembly 不可用、语法 wasm 加载失败或单文件 parse 报错时，该文件自动回退——JS/TS 走正则启发式，其余语言回纯计数（无函数级指标，复杂度会把字符串/注释中的关键字误计）；单文件超过 1MB 也跳过 AST 直接纯计数。
- `--heuristic` 可强制全库走启发式层（用于测试与对比）。降级不抛异常、不中断整轮分析；启发式占比越高，「疑似」结论越多，人工核实的义务越重。

## DDD 启发式的能力边界

报告中的分层归类基于命名与目录约定（如识别 domain、service、repository 等命名模式），属于**命名约定级启发**：

- 能做：按目录与文件名前缀粗分归属，统计跨层引用次数，提示「疑似分层越界」。
- 不能做：判断业务语义、确认某函数真的属于某领域概念、理解隐含的领域规则。
- 示例：报告提示「repository 层疑似反向引用 service 层」，需打开代码确认是真实调用还是仅命名巧合。
- 因此：凡报告标注「疑似」的结论，必须打开代码人工核实后才可写进结论；禁止把启发式输出当事实转述给用户。

## 模型补充分析的角色

脚本与模型分工明确，缺一不可：

1. 脚本给量化底数：复杂度、依赖计数、环检测——客观、可复现、覆盖全量文件。
2. 模型读代码补语义：打开热点文件，判断复杂度是「本质复杂」还是「可消除的偶然复杂」，识别脚本看不见的重复模式与命名失真。
3. 合成结论：在 `report.md` 末尾追加「人工研判」小节，逐条写明「脚本发现 X → 人工确认或推翻，理由是什么」。
4. 拿不准的标注「待确认」，不要替用户下架构判断。

## 产物

- `report.md`：量化报告 + 人工研判小节；后续技能（uncle-bob、system-architect、refactoring-workflow）都以它为现状底数。
- 向调用方回报三件事：最值得处理的 3 个热点、循环依赖条数、被排除的路径清单。

## 何时停

- 脚本运行失败：原样回报错误与所执行的命令，不自行修改脚本接口；缺 Node 环境时停止并告知安装要求。
- 目标路径不存在或为空：停止，向用户确认路径后再继续。
- 报告为空（目标无源码文件）时视为失败：确认路径与排除规则是否把有效代码排除掉了。
- 分析对象规模过大导致脚本明显卡死或内存不足：按子目录拆分逐个运行；仍失败则停止上报。
- 全程只读，不修改任何业务代码。
